## Что проверяется автоматически

| Сценарий | Тип проверки и результат |
|---|---|
| Несколько файлов около 1 ГиБ | Расчёт безопасной вместимости планировщика; большой реальный прогон частичный, см. ниже |
| Файлы около 2 ГиБ | Unit-проверка бюджета; полный реальный обмен не выполнен |
| Файлы около 4 ГиБ | Unit-проверка бюджета; полный реальный обмен не выполнен |
| Торрент 149 ГиБ, файлы по 4 ГиБ | Расчёт 19 партий; общего ограничения 10 ГиБ на торрент нет. Физическая передача 149 ГиБ не выполнялась |
| Данные больше workspace | Реальный loopback BitTorrent: 37 749 291 байт, workspace 35 651 584 байт, три цикла |
| Пограничные части и вложенные папки | Реальные v1-части 256 КиБ, размеры файлов намеренно не выровнены; полное SHA-256 сравнение каждого результата с сидером |
| Пауза/возобновление | Реальный libtorrent, ограничение скорости локальных peers, сохранение resume.bin; новый Engine выполняет recheck и получает тот же SHA-256 |
| Magnet | Реальные metadata exchange от loopback-сидера; полезные .bin в metadata-каталоге не создаются |
| Обрыв сети при upload | httpx.MockTransport: сервер принял половину данных, затем ReadError; следующая попытка продолжает с подтверждённого Range |
| Ошибка Drive / checksum mismatch | Управляемый получатель и HTTP-стенд; локальная копия и резерв сохраняются; число попыток ограничено |
| Потеря ответа после upload | Стабильный preallocated Drive ID и повторный GET; тест подтверждает отсутствие второго создания |
| Восстановление состояния | SQLite закрывается/открывается; confirmed очищается без повторной отправки; незавершённый payload и upload session сохраняются |
| Заполнение диска | Модель free=0 и проверки admission; уже проверенный payload после рестарта отправляется без новых torrent-записей |
| Повторное OAuth-подключение | Локальная замена зашифрованных credentials, чтение новым vault, отказ при неправильном Fernet key. Реальный refresh/consent Google не выполнялся |
| Удаление | Только после confirmed; удаляется изолированный slot; неправильный slot/path отклоняется; ошибка удаления имеет конечные повторы |
| Атомарность | Несколько SQLite-соединений из потоков конкурируют за последнее место; успешен один claim |
| Учет уже записанных байтов | Активный payload не резервируется второй раз поверх своего полного резерва; неизвестные файлы учитываются отдельно |
| Несколько задач | Можно добавлять задачи, когда полезные данные превышают служебный резерв; используется общий бюджет SQLite |
| Доступ | Только OWNER_TELEGRAM_ID в private chat; другой ID/группа не допускаются |
| Входные данные | Traversal до нормализации libtorrent, опасные имена, private HTTPS, credentials в URL, нестандартные порты, DNS на loopback отклоняются |
| Большой одиночный файл | Метаданные 20 ГиБ принимаются и показываются; запуск запрещён до создания полезных данных |
| Один процесс | Второй владелец DATA_DIR не получает файловую блокировку |

Реальный малый прогон на итоговом коде измеряет суммарный логический размер DATA_DIR
каждые 100 мс, с консервативным учётом entry overhead. Он не заменяет проверку
жёсткой квоты: между измерениями возможны записи C++ и файловой системы.
В итоговом завершённом прогоне пик составил **13 200 083 байта** при лимите
35 651 584 байта; суммарные полезные данные — 37 749 291 байт.

## Частичный гигабайтный прогон

Запущен отдельный большой тест: 12 файлов чуть больше 1 ГиБ каждый, сумма
12 884 901 966 байт, рабочий лимит 10 737 418 240 байт. Локальный сидер,
детерминированные sparse-источники с уникальными началом/концом; каждый запрошенный
байт передавался через libtorrent. Получатель Drive заменён PrivateDrive, читающим
файл и вычисляющим SHA-256; реального Google upload здесь нет.

На момент остановки 4 файла (сумма 4 294 967 322 байта) были в состоянии done,
2 скачивались, 6 ожидали. Снимок: LARGE_TEST_OBSERVATION.json. Прогон был остановлен
из-за длительности на локальной Windows-машине. **Он не считается успешным полным
интеграционным тестом**, финальные assertions всей раздачи не выполнялись.
Этот прогон предшествовал последним изменениям учёта резерва/паузы; регрессию
итогового кода проверяет основной набор ниже.

Для полного повтора на Linux/целевом стенде:

```sh
RUN_LARGE_TESTS=1 python -m pytest tests/test_integration.py -q -s
```

В PowerShell: `$env:RUN_LARGE_TESTS='1'`, затем та же команда без префикса.
Включаются наборы 1 ГиБ ×12, 2 ГиБ ×6, 4 ГиБ ×3 с граничными смещениями.
По умолчанию три больших случая пропускаются; это отражается в выводе pytest.
Нужны отдельное место для сидера и время на полную передачу/хеширование. Seed-каталоги
не входят в рабочий том тестируемого worker, как и реальный удалённый сидер.

## Обязательные внешние проверки перед production

1. Получить подтверждение P2P, UDP/TCP, постоянного тома и квоты у Bothost.
2. Собрать Docker на Linux, проверить libtorrent и запуск одним экземпляром.
3. Настроить настоящий OAuth, загрузить результат в приватный Drive, сверить размер
   и контрольные суммы с оригиналом, проверить upload после реального сетевого сбоя.
4. Завершить полные сценарии 1/2/4 ГиБ, в том числе раздачу >10 ГиБ при реальной квоте.
5. SIGKILL/restart и redeploy в каждой фазе, особенно после Google commit до SQLite commit
   и после confirmed до удаления. Локальные тесты восстановления не заменяют этот chaos-тест.
6. Действительный ENOSPC на тестовом томе, а не модель free=0; проверить БД, диск, inode,
   служебные резервы и перезапуск. Не использовать рабочие пользовательские данные.
7. Реальный отзыв Google consent, повторный consent тем же аккаунтом и продолжение.
8. Проверить реальное Telegram-меню/кнопки/владельца, квоты Telegram API и расход RAM.

Одиночные файлы 20/50/100 ГиБ не поддерживаются и не испытывались как потоковая
загрузка. Никаких заявлений об их поддержке эта версия не делает.
