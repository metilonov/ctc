# Почему одиночные файлы больше бюджета пока отклоняются

Последовательное скачивание само по себе не ограничивает диск. libtorrent пишет
части по смещениям в полном файле; sparse-файл может иметь большой логический размер
и накапливать выделенные блоки. Приоритет последовательности не является гарантией
верхнего предела буфера.

До подтверждения хеша целой BitTorrent-части байты нельзя считать достоверными.
Часть может пересекать границу файлов. Drive resumable принимает следующий диапазон
по offset, но уже принятые данные нельзя произвольно исправить в середине сессии.
Удалив принятый диапазон локально, нельзя оставлять в libtorrent прежние have-piece
флаги: сидирование/чтение/recheck будут ссылаться на отсутствующие данные.

Теоретически реализуемо: свой bounded disk_interface/ring buffer, piece verification,
управление запросами с backpressure, освобождение только подтверждённых Drive диапазонов,
журнал состояний сессии, восстановление хеш-контекста и повторная передача при истечении
Google session. Это отдельная реализация хранилища, а не простая установка sequential_download.
Стандартный Python binding не используется здесь как такой backend.

Текущая версия сознательно отклоняет выбранный файл, если его размер + граничные части
+ служебный резерв превышает полезный бюджет. Файлы 20/50/100 ГБ не поддерживаются.
Большой многофайловый торрент допускается, если выбранные файлы по отдельности помещаются.
Заявлять поддержку потокового режима можно после тестов: reorder/corrupt pieces,
обрыв посреди chunk, process kill в каждой переходной точке, истечение session,
повторный OAuth, диск с жёсткой квотой и побайтное сравнение конечного Drive файла.

Источники: [libtorrent storage](https://www.libtorrent.org/manual-ref.html),
[libtorrent partfiles/приоритеты](https://www.libtorrent.org/reference-Torrent_Handle.html),
[Drive resumable](https://developers.google.com/workspace/drive/api/guides/manage-uploads).
