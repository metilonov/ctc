# Cloud Torrent Bot

Python 3.12, aiogram 3, libtorrent 2.0.15, SQLite, Google Drive OAuth.
Интерфейс и документация на русском. Один владелец, один процесс.

**Статус: реализация для приёмочных испытаний, не подтверждённое production-развёртывание.**
Локальный BitTorrent и HTTP-протокол Drive проверяются отдельно. Реальная связка
Telegram → BotHost → Google Drive требует ваших учётных данных и допуска P2P.
Точные выполненные проверки: [docs/TEST_REPORT.md](docs/TEST_REPORT.md).

## Быстрый запуск

1. Прочитайте [проверку BotHost](docs/BOTHOST.md). До разрешения P2P и настройки
   жёсткой квоты рабочего тома бот отказывается запускаться.
2. Установите Python 3.12 x64; создайте окружение:

   ```sh
   python -m venv .venv
   # Linux: source .venv/bin/activate
   # PowerShell: .venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```

3. Скопируйте `.env.example` в `.env`. Задайте BOT_TOKEN от BotFather и свой
   числовой OWNER_TELEGRAM_ID. Бот работает только в личной переписке с этим ID.
4. Создайте ключ шифрования:

   ```sh
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```

   Запишите его в TOKEN_ENCRYPTION_KEY; храните резервную копию отдельно от данных.
5. Выполните [OAuth-инструкцию](docs/OAUTH.md), перенесите зашифрованный токен.
6. После подтверждения условий хостинга установите P2P_ALLOWED=true и
   WORKSPACE_QUOTA_CONFIRMED=true. Эти флаги — подтверждения оператора, они сами
   не устанавливают квоту и не дают разрешение провайдера.
7. `python main.py`. Откройте `/start`, отправьте торрент, выберите файлы и нажмите
   «Начать». Полная структура: `/tree ID`; список кнопками разбит на страницы.

Рабочие данные, SQLite, resume и токены находятся внутри DATA_DIR. Не размещайте
этот каталог в публичном webroot, исходниках или Docker-образе. Используйте постоянный
том, доступный только UID процесса. Бот не создаёт публичных ссылок Drive.

## Устройство

* `bot/` — owner middleware, меню, выбор файлов, статусы по запросу с ограничением частоты.
* `torrent/` — метаданные, HTTPS с проверкой DNS, libtorrent, проверенные части, resume.
* `scheduler/` — очередь, атомарный резерв, отдельный worker на файл, конечные повторы.
* `storage/` — имена, процессный lock, учёт диска и ограниченная очистка каталогов.
* `drive/` — OAuth, Fernet, resumable REST upload, стабильный remote ID, сверка MD5/размера.
* `database/` — транзакционные состояния, резервы, upload URL, ID подтверждений.
* `config/` — ограничения и переменные окружения.

Лимит относится ко всему DATA_DIR, а не к размеру торрента. По умолчанию это
10 × 1024³ байт. 256 МиБ оставлены под SQLite, метаданные и служебные данные;
512 МиБ должны оставаться свободными на разделе. Полезные данные занимают меньше 10 ГиБ.
Один файл 10 ГиБ уже не помещается. Общий торрент 149/300 ГБ допускается, если
каждый выбранный файл помещается с резервом. Неподдерживаемые файлы видны в списке,
а «Все допустимые» выбирает только подходящие.

`SmartStorageScheduler` резервирует размер файла, две граничные части, округление
блоков и 16 МиБ служебного запаса. SQLite BEGIN IMMEDIATE объединяет проверку
бюджета и смену состояния. Уже записанные данные активного каталога покрываются его
резервом, превышение резерва и неизвестные каталоги учитываются дополнительно.
Проверка свободного места на разделе намеренно консервативна. До двух файлов
обрабатываются одновременно; новые задачи допускаются после очистки любого файла,
ожидания всей партии нет. Расчёт партий — оценка best-fit decreasing без учёта
разной скорости сети, числа слотов и динамического заполнения.

Каждый файл загружается **в отдельной сессии и каталоге полного торрента**, с нулевыми
приоритетами остальных файлов. Лишние байты граничных частей хранятся в его partfile.
Данные между сессиями не разделяются: после удаления одного файла следующий
заново получит нужные граничные части. Это требует лишнего трафика, но не оставляет
устаревшую have-piece карту после удаления. Завершение определяется проверенными
BitTorrent-хешами всех пересекающих файл частей. Перед передачей/очисткой ожидается
`torrent_paused_alert`, подтверждающий завершение disk I/O и закрытие файлов.

`queued → downloading → uploading → confirmed → done`. Запись confirmed выполняется
после GET Drive с размером и MD5; лишь затем удаляется весь изолированный каталог.
После падения confirmed очищается без повторной отправки. Для остальных файлов
сохраняется резерв, а libtorrent выполняет recheck реальных данных перед продолжением.
Для проверенных файлов сохраняется MD5 до начала upload: при повторе локальная
копия сверяется с этим digest и сразу отправляется, даже если защита диска блокирует
новые torrent-записи. Незавершённые файлы проходят libtorrent recheck.
Идентификатор Drive выделяется и записывается до начала upload: потеря ответа после
успешной передачи не создаёт ещё один файл. Upload URL хранится в защищённой SQLite
(не выводится в лог); OAuth refresh token зашифрован Fernet.

При ошибках локальные данные и резерв остаются. До 5 попыток с задержкой 10…900 с;
после исчерпания файл переходит в error. «Продолжить» явно запускает новый набор
попыток, в том числе после обновления OAuth. Пауза останавливает передачу после
текущего HTTP-запроса (таймаут 90 с). Отмена окончательна и удаляет локальные
данные задачи; уже загруженные файлы Drive остаются приватными.

## Ограничения

* Строгий физический предел требует внешней квоты. Приложение не может атомарно
  ограничить все записи SQLite, файловой системы и C++ libtorrent через polling.
  При ENOSPC сохраняйте состояние и восстанавливайте свободное место; не повышайте квоту.
* Windows использовалась для локальных испытаний; production-цель — Linux с квотами.
  Docker-образ и BotHost нужно испытать на целевой инфраструктуре.
* Нет подтверждённой потоковой поддержки одиночных файлов, превышающих полезный бюджет.
  [Обоснование](docs/LARGE_FILES.md).
* Метаданные ≤8 МиБ, ≤10 000 файлов, часть ≤64 МиБ, ≤100 задач в истории.
  Историю пока архивируют администраторским обслуживанием при остановленном процессе.
* Статусы обновляются вручную; автоматический push прогресса и точный ETA не реализованы.
* Подключение Google выполняется локальной CLI-командой, а не браузером на хостинге.
* Одновладелец и SQLite — текущая модель. Публичного Android HTTP API пока нет:
  [будущий контракт](docs/ANDROID_API.md).
* Без поддержки private tracker cookies и web seeds. Ссылки с redirect отклоняются.
* Кэш папок привязан к Google-аккаунту. Переподключайте тот же аккаунт; для смены
  аккаунта остановите бот и заведите новый DATA_DIR, иначе IDs относятся к старому Drive.
* Утрата ключа шифрования потребует повторного OAuth. Бэкап без ключа не восстановит токен.

## Тесты

```sh
pip install -r requirements-dev.txt
python -m pytest -q -s
ruff check .
```

Большие локальные тесты: `RUN_LARGE_TESTS=1 python -m pytest -q -s` в Linux;
в PowerShell сначала `$env:RUN_LARGE_TESTS='1'`. Они передают несколько раздач
по 12 ГиБ через loopback и используют отдельные каталоги сидера за пределами
ограниченного workspace. Нужны время, свободный диск и RAM тестовой машины.
Сидовые файлы sparse, но каждый байт проходит через BitTorrent; получатель записывает
обычные файлы, а SHA-256 сравнивается полностью. `python -m scripts.preflight`
выводит локальные возможности без секретов; права P2P и квоту он не проверяет.

Тестовые торренты создаются из контролируемых повторяющихся байтов и передаются
локальным сидером. Пользовательские/чужие файлы и публичные раздачи не используются.
Docker: `docker build -t cloud-torrent-bot .`; способ подключения тома и квоты описан
в [docs/BOTHOST.md](docs/BOTHOST.md). `requirements-tested.txt` фиксирует использованное
при испытаниях окружение; для другого ОС используйте основной requirements.txt.
